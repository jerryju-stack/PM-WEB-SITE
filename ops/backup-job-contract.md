# 备份调度接入契约（未安装）

已确认：北京时间每天 00:30、12:30，RPO 24h，全天 RTO 8h，每次计划停服 ≤5min，快照至少保留 30 天。config/backup-policy.json 是默认策略，修改它也必须提交运行代码。两个窗口间隔 12h，留出一次失败后的告警/补跑空间；RPO 是否满足应看最近有效恢复点，而不是 cron 是否执行。

project-station-backup.timer.example 只交付声明，**未安装/启用任何本机、生产或 Codex 定时任务**。它的 service 必须由部署负责人结合实际进程管理方式接入，不能猜测现有 unit 名称、数据目录、备份磁盘或重启权限。本轮没有连接服务器。激活前在生产副本和目标 OS 验证服务适配及计时。

一次正式调度的处理程序必须执行以下顺序：

1. 检查策略/配套代码已提交、备份位置独立且空间足够、当前为批准窗口，并记录停服开始时刻。
2. 拒绝新写入，停止实际应用单元，等待该进程退出；核实数据目录锁可用。不是简单执行一个返回即算停服。
3. 运行 `node --experimental-strip-types scripts/backup-policy.ts run --data DATA_DIR --root BACKUP_ROOT --offline-confirmed yes --scheduled yes`。离线参数是运维确认，不会使工具自动停止服务。在线目录仍会被锁拒绝。
4. 无论备份成功还是失败，都尝试启动原应用并检查业务可用；停止、备份、重启、验证的**总时长**不得用单独复制耗时代替。工具给备份阶段 4min 预算（总额的 80%，另留 1min 给外部停服/重启/核验），在阶段边界检查，但不提供硬实时中断或控制外部服务。实测总停服超标必须告警，不能宣称目标兑现；文件系统单次阻塞可能超过检查间隔，正式适配器还需超时和 finally 恢复服务。
5. 运行 status，检查 JSON alerts 与退出码。每次运行失败写 BACKUP_ROOT/state.json，不推进 lastSuccessAt；调用方必须记录 stderr/nonzero 并通知值守人员。本地持久化告警不是已送达的短信/邮件。当前没有通知账号/通道/值守安排，待运维接入，不向外发送任何消息。
6. 仅在新恢复点成功、源服务已恢复、状态正常后，按保留预览执行受控过期清理。禁止失败后顺带清理唯一旧恢复点。

建议目标调度器另每 5 分钟执行 `backup-policy.ts status --root BACKUP_ROOT`，由调用方持久化/处理 exit=2。status 检查错过窗口、最新有效恢复点超过 24h、损坏、最近失败及运行中断；退出码 0 表示本地状态健康，并不认证生产 RTO 或独立副本可用。首次运行前无 catalog/无恢复点是失败，不能忽略。

`retention --data DATA_DIR --root BACKUP_ROOT` 默认预览。`--apply yes --delete-expired-confirmed yes` 才永久移除**本工具目录清单登记、校验完好、超过 30×24h**的快照；恰好 30 天保留，最新有效恢复点始终保留。没有新鲜恢复点、最近运行未成功或已登记快照损坏时拒绝删除；未知目录、其他数据集、源 uploads 和附件 quarantine 不受此命令管理。清理前再次核对真实绝对路径在备份根内，不跟随软链接。目录须仅授权运维可写，避免外部并发修改。删除中断可能留下无效目录/catalog 残留，status 会报告，必须人工排查，不能自动扩大删除范围。

30 天是完整快照的最低保留窗口，不是附件隔离区清空授权。隔离区无自动永久清空。每 12h 一套约 60 套，需按实际 DB+uploads+quarantine 总量预留磁盘及增长空间。单机磁盘损坏、备份位置同盘、取不到依赖/配套代码、无人值守等仍会使目标无法兑现，必须在启用前解决。
